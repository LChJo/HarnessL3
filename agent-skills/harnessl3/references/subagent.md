# Delegated tasks and parent handoffs

For delegated work by existing Codex/Claude Code agents. L3 does not launch, select or schedule agents; delegation depends on user authorization and actual host capabilities. Do not duplicate the parent's entry workflow.

## A usable parent handoff exists

The parent provides the actual worktree/path, taskId, delegated goal/scope, version binding, handoff through a known batch and necessary archived skill references. It may include already-returned bodies with their source and actual reader identified; a parent's read is not an observed child CLI read. Declared parentage is not CLI-observed causality.

1. Reuse complete identifiable project context. Only lost material or a necessary batch check needs task handoff with the actual taskId/batch; preserve the parent's joint selection.
2. Each user turn, reassess skills within the delegated scope and reuse suitable identifiable bodies already provided; read only missing selected files/context. A different skill set needs an authorized independent task; do not append a stage to the parent's task without an explicit handoff authorizing it. Use command help for shorthand and recorded references.
3. Execute only the delegated scope. Return actual results, read/write/review coverage, missing material and relevant task/batch references. Do not close the parent, reselect its skills or expand the assignment. The parent owns overall synthesis, synchronization and closure; a local result is not full-parent verification.

Report a closed task, target mismatch, changed-version need or incomplete handoff as a specific conflict. If an authorized independent current-version context or different skill selection is necessary, create your own task; never append new content to an old binding or replace the parent's archived selection.

## No usable parent handoff exists

Use the actual existing worktree and delegated goal with the main skill's ordered routing. Establish your own entry and one selection, explicitly empty if appropriate. Keep identities, bindings and status separate. Plans/replies do not automatically close your task; close after the actual delegated scope is complete/cancelled and synchronization is recorded.

If target, tools or materials are missing, tell the parent what is needed. Do not guess the latest project, create Git/worktrees or fabricate a successful call. Install/onboarding recovery follows the main skill without recursively creating setup tasks.

## Capability boundaries

Current compatibility uses ordinary task/handoff/query/archive commands; there is no parentTaskId field, child scheduler or dedicated permission isolation. Parentage is a handoff declaration; do not invent JSON fields or claim the CLI enforces parent-close restrictions.

Log collection still requires an authorized known host/session/absolute path. Do not auto-bind or recursively scan child sessions, or expand the supported Codex/Claude Code host list.
