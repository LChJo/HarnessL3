# Agent CLI可靠性与同步恢复

## v0.49：同步恢复（2026-11-12）

用户反馈agent反复遇到SYNC_RACE，只留下“已有版本竞争问题”。截图脚本从sync status起头且后续被截断；代码中的SYNC_RACE由sync verify产生，不能据首行认定单独status查询抛出了它。本轮没有访问或修改截图中的其它项目，而是在独立合成worktree重现机制。

- 原watchEvent把所有`.git/**`事件当作观测缺口，临时锁、reflog、对象pack和FETCH_HEAD也推进epoch；五个无源码变化通知便使隔离基线从0变为5。修复只过滤确定的维护路径；显式证据引用、关键/聚合/未知Git通知继续失效，包括index、HEAD、refs、config、info/exclude与objects/info/alternates。
- 原status只补采一次；连续两次写入后仍返回scanPending。现在只读查询有界重新执行完整采集并等待路径分类，稳定后返回新的绑定；持续写入则保持pending，附SOURCE_CHANGING及下一步。没有使用mtime、增量结果或固定静默等待冒充完整核验。
- 语义声明不自动重基。verify仍保留两次完整采集、提交队列内复核、版本/策略/模型/epoch比较和字节回退保护。SYNC_RACE返回明确原因、reviewRequired、reviewScope及当次current；同requestId原样重放旧回执。agent在既有授权内刷新事实、重审实际范围及checks后提交新声明；持续活动须说明具体待核验范围和下一步。

初始命令`node --test --test-name-pattern='Git lock and reflog|status absorbs a bounded burst' tests/v1/freshness.test.mjs`两项均失败（epoch 5≠0、scanPending true≠false）；修复后二项通过。加入持续写入、真实Git元数据和结构化恢复/回放检查后，针对性五项全部通过。原有字节回退、来源未知、模型无效、链接/证据异常及局部scope保护继续纳入回归。实际完整测试、包和平台结论见[实施状态](STATUS.md)，报告保存在本机忽略目录，不用程序或文案测试冒充真实宿主语义加载。

进一步以两个独立合成Git工作区调用真实CLI，并持续写入已有reflog：旧2257c91构建在156次写入时返回SYNC_RACE且源码版本未变；修复版在98次写入时成功verified。探针最初的重复清理hook在夹具删除后执行，已修复探针后重跑，不记为产品失败。Windows完整程序回归402项（398通过/4跳过/零失败）及同步/CLI/安装器51项通过；原生差分、JUnit与后续包报告保存在`.harness-local/validation/sync-recovery/`。

本机候选包162文件/409062字节，真实npm消费者的安装/重装、26方法与双宿主复制、bin/实际服务构建/认证RPC、旧交接比较及差异拒绝、无Git目录/Edge157浏览通过。该包来自modified source，本机从干净GitHub源码更新及最终原生CI结果保留各自实际构建来源，不把候选验证冒充已交付的干净构建。

## 已确认的问题与改变

| 问题 | 最终机制 |
| --- | --- |
| 少量上下文也前置多次完整源码检查，期间静默 | 默认snapshot只捕获合法模型和技能目录，来源unknown/策略null；query从原模型归档读取。显式verified及sync核验仍执行完整双遍检查与严格CAS |
| 等待终止后不知是否执行，也难找请求ID | stderr先报告ID及阶段，认证进度查询提供恢复/模型/扫描/排队状态；CLI有可配置总等待预算。超时/取消不撤销已接受工作，unknown不自动重发 |
| 默认请求ID只在最终响应出现，缺独立回执查询 | request status在明确目标内返回running/completed/unknown及原回执。重启从原journal和引用恢复；非持久管理结果丢失保持unknown，不伪造未执行 |
| 模型手工搬运绑定、known和文件哈希 | CLI接受批量快捷参数，缺省任务绑定/模型版本和空集合；文件哈希从所选历史方案解析。显式字段仍严格校验，known默认{}，原提交意图维持重试身份 |
| 换技能需要另开任务，每轮机械重读 | 同任务--stage显式追加方案，旧批次的packet/catalog/plan/原字节保留。适用且仍在上下文的正文可复用，缺失才读；新模型或verified来源绑定另建任务 |
| 内层错误转换隐藏权限原因 | 来源、配置、技能目录、模型及归档读取保留原生拒绝字段；实际权限与宿主无法创建进程仍区分，不改ACL/数据根绕过 |
| 历史payload与累积批次长期驻留、派生索引重复正文 | journal流式逐行核验，仅驻留提交头/引用/字节定位；按需读取再核原指纹。任务缓存与响应缓存有界，批次索引只存定位和计数所需字段 |

服务保持单实例、原数据根与单写提交队列。请求进度不是第二套历史，已完成回执的暂存不替代档案；同ID在途同意图共享执行，不同意图拒绝。重启或淘汰后的管理请求不获额外“恰好一次”保证。

默认总等待预算为120000ms，可显式调整。安装校验将剩余预算传给子CLI，避免外层允许180秒、内层30秒先终止。该预算依据实际旧历史恢复成本调整，不是耗时保证；进度与原ID查询在预算耗尽后仍是必要恢复路径。

## 失败回归及验证方式

- `request-recovery.test.mjs`：静默RPC、有界等待、早期ID、原回执跨重启查询、目标隔离、在途去重与限流、启动失败封套、提交后丢失/超时响应不会重复写入。
- `agent-flow.test.mjs`：嵌套仓库不阻塞模型快照，来源保持未知；verified仍拒绝不完整来源。快捷参数和同任务阶段保留历史方案/技能字节。
- `archive.test.mjs`：约96MiB合成日志在64MiB堆上，旧实现实际以堆耗尽退出；修复后逐条恢复，原日志大小与原内容寻址语义保持。此为隔离合成历史，不操作用户档案。
- `permission-errors.test.mjs`：只在自建临时目录限制并恢复ACL，覆盖描述、锁、技能复制、来源和快照读取；正常宿主运行不冒充受限宿主审批验收。
- 原verified测试显式使用该模式，继续核对来源变化、目录无Git运行、身份原地转换、严格epoch/CAS、损坏拒绝和旧回执；不通过放宽断言消除保护。
- 全量暴露的目录→Git竞态：新身份不能复用仍在返回的旧目录刷新；身份代次不同先等待旧刷新结束，再完整重扫。保留资源和UUID，新增可控交错回归，来源变化的严格核验不降低。

## 真实项目观察

`I:/aimana/ai_mana_front_debug`原实现复现一次task start为151917ms，结束前stdout/stderr均为空。本轮候选在服务恢复六个已有工作区、并发验证负载下，首次模型快照入口58051ms，随后两次1114ms/1388ms；首次HarnessL3自身历史恢复99539ms。样本并非同一冷启动对照，不把热启动改善当作冷启动或SLA。完整旧历史仍需校验，不能声称所有命令均在数秒内完成。

原项目四个.harness配置/模型文件SHA-256前后相同。首次全局安装校验的旧handoff在30秒子CLI预算下返回REQUEST_TIMEOUT；随后用原requestId查询得到completed、原receipt.ok=true，再进行只读交接比较，不把超时当未执行或重发写请求。旧包、原handoff和失败封套保存在工作区外临时证据目录；本机报告见实施状态。

完整运行、安装消费者、浏览器及平台数量以[实施状态](STATUS.md)和本机`.harness-local/validation/reliability/`报告为准。真实受限宿主的进程创建/审批链、未实际运行的平台不补称通过；没有发布npm或自动提交授权。

最终全局候选在原数据根安装验证通过，旧packet/skillPlan/binding完全匹配（143210ms，包含恢复与检查）。AI Mana默认参数三次入口均成功：19963/1130/1177ms；该组与前组负载、恢复状态不同。默认120秒可调，跨工作区大历史冷恢复仍无数秒保证。
