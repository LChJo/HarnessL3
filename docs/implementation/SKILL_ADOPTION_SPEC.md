# 复杂任务规划与技能采用优化规格

2026-11-22 · 已确认 · 基准 v0.55

本规格细化 [SA01–SA04](SKILL_ADOPTION_PLAN.md)，对应 D06、D09、D13–D15，FR05、FR06、FR12、FR15 及 TC19、TC22、TC26、TC27。覆盖入口判断、方法交付与采用、真实宿主验收及原版本恢复。实际验证见[实施状态](STATUS.md)。

## 问题与目标

近期 316 条 L3 任务中有 59 条选了技能，54 条至少取得一份正文。已定位的会话既有使用访谈方法、等到用户回答后继续的实例，也有跨层删除在选取实施技能后直接修改的实例。项目还存在 L3 空选但已有本地规格和任务清单的情况。选择、完整交付、按方法行动和开工前审阅需要各自的证据。[本机调研](../research/local-skill-adoption-2026-11-22.md)

新复杂任务在首次依赖方案的修改前，有一次可观察的方案审阅或决策确认。用户可以在范围和验收明确后推进，遇到关键取舍才需要回答问题。已确认的方案可跨轮继续使用。当前 agent 根据实际目录取得并采用所选方法，CLI 继续提供目录、正文和可追溯回执。

## 用户场景

1. 作为提出跨模块改动的用户，我希望先看到变更边界、实施顺序和验收条件，再决定开工。
2. 作为提出兼容性、迁移或权限变更的用户，我希望 agent 先查事实，再就会改变结果的选项给出建议和取舍。
3. 作为只要求调研、讨论、规格或拆票的用户，我希望当前轮交付相应成果，并保留后续实施入口。
4. 作为已确认方案的用户，我希望回复“按这个做”即可推进原范围，后续发现实质变化时只重审变动部分。
5. 作为明确要求先列计划再执行的用户，我希望 agent 按已给的授权继续，对尚未交给它决定的关键取舍单独确认。
6. 作为只需要小修的用户，我希望 agent 直接完成明确工作，并遵守项目已有检查约定。
7. 作为明确点名方法的用户，我希望使用当前目录里的实际名称和版本，目录缺项时能看到具体情况。
8. 作为在分轮访谈中作决定的用户，我希望 agent 依真实回答推进，并保留未决事项。
9. 作为从旧批次继续工作的用户，我希望 agent 找回原方法正文和已有决定，正确处理当前库已经更新的情况。
10. 作为维护者，我希望能分别验证正文交付、实际采用和方案确认顺序，并复现基线和候选的差异。

## 开工前判断

**当前意图优先。** 每轮先结合当前请求、要操作的目标、已读的规格或票据，以及用户实际给出的授权判定当前阶段。只读调研、诊断和项目事实核对可直接推进。仅要求讨论、写规格或拆票时，交付对应材料。规划产物可按已获授权写到项目现有位置。

**复杂度看决策和影响。** 出现以下任一情况时先按复杂改动处理。先用只读检查缩小范围，发现原问题实际是有明确验收的小修时可以据实改判。

- 跨组件变更职责、接口或数据流，需要协调实施顺序或联合验收。
- 改变公开契约、持久数据、兼容策略、权限、迁移、故障恢复或发布回退行为。
- 存在会影响结果的方案取舍，或者用户可见行为、改动边界和验收标准仍有重要不确定性。

首次修改的分界是首个会改变目标行为或外部状态的工具调用。源码、配置、行为测试、迁移和部署等都计入对应目标的实施。已经授权的只读调查和方案草拟可以在等待答复时继续；依赖待确认决定的业务修改在确认后才开始。

| 已知条件 | 当轮应交付或执行 | 继续条件 |
| --- | --- | --- |
| 有实质未决事项，现有资料不能确定 | 先查事实，再询问仍需用户决定的问题。每题给推荐和取舍，按依赖分轮。当前宿主提供且允许原生询问工具时实际调用 | 收到真实回答后更新方案。缺少可用工具时，在可见的审阅稿或回复中留下问题和等待状态 |
| 需求清楚，复杂改动尚无可执行的方案 | 在对话或现有项目文档位置提交短计划，写清影响边界、关键决定、实施顺序和验收。需要长期约定时起草规格 | 用户确认可见方案后推进。单独一句“做这个”确定目标，与具体方案同范围的实质确认才可复用 |
| 需要独立交付或安排跨切片依赖 | 基于已有方案呈现可独立验收的切片、各自交付和阻塞关系。沿用现有本地票据或已授权的跟踪流程 | 复用已确认的拆分；剩余粒度或依赖问题确认后记录并推进 |
| 已确认方案、单票或整份规格，目标和验收仍适用 | 读取相应材料，按已确认范围实施 | 范围、验收或回退策略发生实质变化时，仅就变化部分重新确认 |
| 用户明确授权先列计划后直接执行 | 先给出可见短计划，再在明确授权范围内推进 | 尚未委托且会改变结果的决定仍需确认 |
| 简单问答或目标、位置、改法已明确的低影响修改 | 直接执行并完成项目要求的检查；仅在满足当前目录中 `quick` 的正文条件时选用该方法 | 碰到诊断、设计或实质风险时重新判断阶段 |

用户的实际回答、明确委托或可核对的批准记录是继续依据。预选项、异步询问工具返回、沉默和 agent 的计划摘要都缺少批准证据。讨论中的最后一次确认已覆盖可见方案的范围、关键决定和验收时，可以直接推进。若仅回答了一个分支，就更新方案并留待完整审阅。首次项目接入继续适用单独的询问契约。

## 路由与采用

### 入口文案和方法选择

将上面的开工判断放到运行时入口的首段，并在 `task start` 和 `task prompt` 共用的 `routingPrompt` 前部表达相同规则。两处都写清“先判当前阶段”“复杂且未有已确认方案时先讨论或交计划”“获得完整正文后落实该方法”。运行参考承载完整决策表、长响应恢复和冲突处理。用现有 `routerVersion` 标识新路由语义，JSON v1 封套和文本单次展示规则沿用现有契约。

供实现时使用的提示主句如下。

> 先判断用户本轮要调查、讨论、规划还是实施，并核对当前目标与已经确认的验收条件。复杂改动进入实施之前，先解决会改变结果的决策，或交付可审阅的方案并等待确认。复用适用于原范围的明确授权。按当前阶段从实际目录选方法，拿到完整正文后，落实本阶段的动作、等待条件和交付物。

目录条目按真实 ID、描述和版本匹配。显式 `grill-me` 或 `grillme` 使用实际存在的独立方法。普通访谈对应 `grilling`，需要同时维护术语和决策时对应 `grill-with-docs`。缺少点名方法时说明实际缺项，按当前授权提供可用路径。目录没有合适方法时允许空选，开工判断仍按用户意图和已有确认执行。选的是哪个方法，以实际方案和归档正文为依据。

随包默认简述突出触发条件。访谈针对存在待定决策的任务，写规格针对目标已定且需要形成可审阅的实现说明，单项实施针对已有验收条件的已确认单票、规格或短计划，整份实施针对已有规格及可用的依赖票据。单项实施正文与短计划的适用说明同步。票据方法用于需要切片和依赖排序的工作。复用既有 ID 与可编辑目录，CLI 从运行时目录取候选。正常更新按安装约定保留活动用户库及 junction，旧描述的用户库同样由入口规则判断阶段。

### 读取后应用到本阶段

在同一批次联合选择必要的项目材料和当前方法。理由说明这份方法怎样帮助当前阶段。多个方法可分别服务本阶段的不同输出，后续阶段需要的正文在真正转阶段时取得。遇到冲突时按用户授权和项目规则解决，仍需决定的分支保持待确认。

取得完整正文后，当前 agent 依据方法确定接下来的动作、需要等待的条件，以及何时交付或转换阶段。访谈落实到问题依赖、推荐与等待答复。写规格落实到可审阅的产物和验收。拆票落实到切片、阻塞关系和用户确认。实施落实到已确认范围及对应检查。用实际动作和产物验收，技能名、自报采纳和原生加载记录各自只说明其所记录的事实。

## 完整交付与续轮恢复

1. 保留 CLI 原退出码、分开的 stdout/stderr 和完整封套。先判定 `ok`，再读取结果或错误。读取 `task start` / `task prompt` 的完整规则，从结构化目录筛选必要候选。使用 `task prompt` 刷新尚未选择的目录。保留请求 ID，发生丢响应时先用原 ID 查询结果。
2. `task select` 可用现有 `--compact` 接收当次正文、技能方案和 `packetRef`。需要累计包时按原任务和边界批次调用 `task handoff`，并核对引用哈希。对方法正文使用 `task read`，核对目标、任务、批次、技能、路径、字节数和哈希。正文和确需的同方法附件进入当前 agent 可用的上下文。
3. 宿主截断工具结果时，从完整原回执取得缺失段，或读取同一归档批次的单个必要文件。执行侧以可用的完整正文为准。显示摘要、落盘、哈希相符和尾部缺失各自按实际情况记录。遇到 `partial` 时保留成功项和错误明细。按实际错误校正批次或文件引用，再差量补取缺项。正文仍缺失时，说明具体受影响的方法和阶段，继续可独立完成的工作。
4. 相同目标、有效绑定、适用正文仍在上下文时直接复用。相同适用模型中需要换方法或版本时用 `task select --stage` 增加批次，仅选缺失内容。所需模型或已验证来源绑定变化时按现有规则新建任务，继续使用核对后仍适用的用户决定。选取、恢复及状态查询维持原有观测含义。
5. 压缩、跨模型或交接造成材料丢失时，先按原任务及原批次恢复引用，再取得所缺的原字节。当前库有新版本时依旧以被恢复批次为准。原档案损坏、缺失或批准记录无法确认时保留相应的未知或待确认状态。归档读取、技能读取和浏览沿用 60 天留存契约。等待决策期间保持任务开放，完成已记录的实际工作范围及阶段同步后收尾。

## 验收

**程序验收使用现有真实 CLI 子进程和隔离档案夹具。** 按 TC19、TC22、TC26、TC27 检查开始和刷新返回完整且一致的路由规则、真实目录新增或改名可见、显式空选、长正文尾部可恢复、partial/错误及原请求回执。对比完整与 compact 返回的数据和恢复哈希。验证同任务从规格或票据转实施、读取旧批次原字节、留存不延长和旧用户库保留。刷新、阶段切换、安装消费者和历史回放沿用现有接口。用可观察行为断言，避免把候选文案逐字匹配当作宿主验收。[当前验收矩阵](../spec/acceptance.md)

**宿主验收先保存当前基线，再与候选对照。** 使用明确授权的隔离会话，固定任务输入、工作区初始状态、宿主和模型标签、运行模式与工具能力。Codex 和 Claude Code 分组，普通执行模式纳入实测。每组核心场景在多个新会话中重复；附加无方法正文对照用于判断方法特有行为，其他输入一致。删除示例中的同名方法提示等混杂信号。跨轮、压缩和跨模型恢复按真实能力分别留证，无法采集的场景记录为未知或待测。

| 场景 | 可观察通过条件 |
| --- | --- |
| 有兼容取舍的跨层删除 | 先检查事实，给出兼容取舍并调用实际可用的询问工具。答复前目标保留原样；收到答复后，首次改动与所选兼容方案一致 |
| 宿主缺少询问工具，或异步询问尚未得到回答 | 缺工具时，未决问题和等待原因对用户可见。异步提交后等实际答复。两种情况下只推进独立工作 |
| 目标明确但缺方案的跨模块改动 | 用户在首次修改调用前看到边界、顺序和验收。暂不答复或拒绝时保持等待；用户确认后进入实施 |
| 用户仅要求规格或票据 | 交付可审阅的规格，或带验收和阻塞关系的切片。续轮收到明确的实施指令后才转换阶段 |
| 用户已确认范围，或要求先列计划再执行 | 读取实际方案和相关验收，给出执行范围。现有授权覆盖同一范围时直接推进；若授权明确允许先列计划再执行，可见短计划先于首改 |
| 明确的小改，以及简单请求转为复杂问题 | 小改直接完成既有验证。发现影响升级时，在触及更大范围前展示方案或咨询决策 |
| 目录大、正文长且尾部有方法特有要求 | 能在宿主工具记录中核对完整正文和实际尾部动作。截断后恢复原回执，partial 或错批次按正确引用差量补读；缺项时保留相应等待条件 |
| 当前库升级后继续原阶段 | 压缩或交接后恢复指定批次的原方法，核对实际字节，并据原方法继续。后续新阶段采用当次所选版本，历史批次可重读 |

每例记录 CLI 和入口版本、实际技能 ID/批次/哈希、宿主与工具能力及相关事件顺序。以真实用户问题、工具结果、计划可见时间、回答和首改调用判定。分别报告选取、完整交付、按方法行动、审阅顺序和任务结果。首改早于必要确认、正文尾部丢失却声称完整交付、简单任务被多加一轮等待均单列失败。缺原始证据的行为保留未知；验收结论限于实际运行的宿主和版本。

对照使用同一份隔离演示工程，准备一个设置页、配置读写层、启动配置读取层，以及含旧字段和用户自定义值的夹具。演练者先发「移除运行工具设置和相关接口」，保留旧配置处理的取舍，直到实际提问后才答「保留读兼容一个版本，所有写入停用」，再按可见方案确认。第二个输入明确相同的兼容规则与验收，等候 agent 先交短计划，再发送「按这份方案实施」。直接实施对照在首轮给出这个已确认方案，小改对照只要求修正设置页一处明确的文字错误。各次恢复使用对应任务与批次，原始日志留在本机授权路径，公开结果只记必要时序与指纹。

## 实施顺序与边界

1. 保存当前版本及隔离基线会话，固定核心场景与观察条件。
2. 分别实施 SA01 的完整交付和 SA02 的阶段判断及方法采用。各自验证程序契约，合并后核对两处提示的一致性、当前目录和正常安装。
3. 用 SA01 路径验证 SA04 的原版本恢复。通过 SA03 比较当前与候选的真实行为，并记录未采集范围。基准、用户入口、契约、验收矩阵和实施状态随获批准的改动更新。
4. SA05 作为后续独立评审，依据真实宿主压缩和恢复结果决定是否需要原生适配。

工作沿用当前 agent 主动调用 CLI、项目文件为权威、文件归档及明确会话只读观测的产品边界。现有审批、接入、同步、工作区隔离和回执规则继续适用。候选验证使用隔离数据及明确授权的会话。CLI 的观测字段仍表达已产出的目录、选择和正文回执，实际行为由宿主证据确认。
