# 近期本机 L3 技能采用与复杂任务规划

2026-11-22，关联 D09、D13、D15，FR05、FR06、FR15，TC19、TC27。调研使用本机 HarnessL3 0.1.6（构建 f2b7635）的用户数据根，并保留各历史任务当时的选择和回执。本文给出优化建议，产品基准仍为 v0.54。

## 结论

本机近期任务确实调用过返回的技能正文，并有后续行为与方法相符的证据。316 条 L3 任务中，59 条选了技能，54 条至少成功返回一份正文，51 条为所有曾选技能留下正文回执。实际遵循率需要宿主行为证据，本机样本不足以估计。

未发现 CLI 把某次成功返回的正文串成另一个技能。更明确的缺口是当前 agent 有时边执行边补选，或把“用户明确要实现”直接理解成“影响范围、兼容性和验收已明确”。已核实一个跨层删除案例在选择实施方法后、未见新的讨论或计划审阅时进入修改。另有复杂任务确实先写了规格再切到实施，也有项目在 L3 空选时留下自己的规格与任务清单。空选可作为排查线索，不能用来统计直接开工率。

建议优先调整运行时入口和 CLI 路由提示，明确复杂度和当前阶段，再要求读取并使用所选方法。复杂任务开工前给用户可审阅的方案，只有会影响结果的决定才发问。已有确认且当前请求明确进入实施时，直接复用其范围与验收。

## 2. 技能返回是否准确

**返回准确性。** 60 组成功返回的正文均与对应批次引用匹配。Joi SDK 主导执行规格任务 `9b5297fe` 先有一条 `SKILL_FILES_FAILED / SKILL_NOT_SELECTED`，随后拿到 `to-spec` 对应正文，已选的 `research` 在调查窗口内无成功正文回执。仅凭回执无法确定前一次失败是时序、批次选择还是其他调用问题。当前路由提供目录和简述，任务侧 agent 在 `task select` 请求中提交 ID 和理由。选择偏差发生在当前阶段与方法匹配这一环，成功的字节返回无需因此换机制。见[路由实现](../../core/context.ts#L373)、[归档正文读取](../../core/context.ts#L563)。

**选择准确性。** 逐条筛查 59 条有选择的任务标题和选取理由，再用重要案例的原始消息、当前或归档方法正文补核。自动生成的标题和理由会遗漏用户条件，所以不计算总体准确率。典型对应关系如下。

- 访谈明确请求匹配 `grilling`。11-17 原任务在独立 `grill-me` 恢复前，使用当时目录中的 `grilling` 是合适的。恢复后的独立条目继续服务显式请求，常规发现阶段优先选[普通访谈](../../skills/discovery/grilling/SKILL.md)，需要同时记术语和决策时才用[访谈与文档](../../skills/discovery/grill-with-docs/SKILL.md)。
- 规格草案匹配 `to-spec`。例如 Joi 目标路径任务 `e11edcf4` 先追加规格阶段、返回正文，后追加实施阶段、返回 `implement-spec`。同一任务的两个阶段相隔约 24 分钟，实施理由记为已批准，能核对正式阶段顺序及已保存的规格，真实批准消息不在本样本中。Joi SDK 会话所有权及增量知识留存也各有规格和后续实施记录。
- `to-tickets` 唯一选择出现在 HarnessL3 的技能优化待办 `d53abded`，同一批还选了 `writing-for-agents`，两份都无成功正文回执。后来返回的 `grill-me` 属独立验证阶段。现有待办确实列了依赖与验收，尚不足以证明采用了票据方法里的切片与用户核对流程。见[当时的技能优化待办](../implementation/SKILL_ADOPTION_PLAN.md)。
- `3641f551` 的第一阶段选 `quick`，理由直接写“再验证 GitHub CI”。[该方法](../../skills/development/quick/SKILL.md)明确排除需要排查或验证的任务；随后切到 `diagnosing-bugs` 并成功拿到正文，首选有可核对的偏差。
- `fd042e0d` 选 `implement`，其正文要求基于规格或票据并先处理会影响结果的歧义。实际用户请求明确了删除目标，档案和宿主行为未显示实施前已有对应规格或票据。当前路由欠缺一个“是否已具备开工条件”的判断。同一时期还有无 L3 技能选择但产出正式规划的例子，Codux 的 Git 评审改版含 proposal、design、spec 和 tasks，提交为 `16cfd201`。工件证明项目规划存在，无法单独确定首个业务文件修改的时间。

## 3. 建议补充的提示

已安装 Codex 与 Claude Code 的入口正文和仓库入口文件哈希一致。当前实际 `routingPrompt` 用了 “The current agent continues its standard workflow”，以及不同工作不必共用固定流程的提示，却缺少开工判定和等待条件。入口也主要说明如何选和读，文末的权限/观测说明没有对应的采用动作。把目标阶段放在入口首段和 CLI 路由前部可直接处理这两个问题。依据见[运行时入口](../../agent-skills/harnessl3/SKILL.md#1-route-the-current-turn)、[运行参考](../../agent-skills/harnessl3/references/runtime.md#continuation-and-skill-routing)及[路由正文](../../core/context.ts#L373)。

### 开工前判断当前阶段

> 首次进入修改之前，先核对用户本轮要的是调查、讨论、规划还是实施，并查看有没有已确认的规格、方案或票据。跨组件改变职责，变更公开接口、数据、权限、兼容性或迁移行为，存在多个有实质取舍的方案，或验收边界仍不确定时，按复杂任务处理。
>
> 有影响范围、行为或验收的未决事项时，先查现有证据，然后用宿主可用的询问工具提出需要用户决定的最小问题，给出建议和取舍，等到真实回答再开始依赖该答案的工作。目标已清楚但尚无实施方案时，先交付一份可审阅的短计划，写清变更边界、关键决定、实施顺序和验收。需要长期规格时起草规格；存在可独立验收、需要安排依赖的增量时再拆票。新的复杂改动默认在交付方案后等待确认，再修改业务文件。已经批准的同一范围可直接推进；用户明确要求跳过审阅时，仍先说明短计划并复用其授权。
>
> 从当前目录按阶段选方法。选择后取得所需完整归档正文，把它的动作、等待条件和交付物落实到当前阶段。方法未到达时按实际批次补取，已保留且版本匹配的正文可复用。进入实施时使用既有阶段切换机制。简单、目标和改法清楚且无需调查或额外验证的工作可直接处理。

简述优先修改三处。让 `grilling` 能按未决决策触发，让 `to-spec` 能按“已能定方案但尚无可审阅规格”触发，让 `implement` 与 `implement-spec` 说明进入实施所需的现有方案、范围和验收。基于明确决定生成规格时，用 [to-spec](../../skills/planning/to-spec/SKILL.md)整理现有结论。存在可独立验收的切片与实质依赖时，用 [to-tickets](../../skills/planning/to-tickets/SKILL.md)先呈现拆分并核对粒度和阻塞关系。保留 [implement](../../skills/development/implement/SKILL.md) 和 [implement-spec](../../skills/development/implement-spec/SKILL.md) 对单一明确范围和整份已确认规格的适用差异。方法仍按实际目录发现。

### 下一轮怎样验证

在现有 [SA01–SA03](../implementation/SKILL_ADOPTION_PLAN.md) 下，对照当前与候选提示，固定一个有兼容取舍的跨层删除、一个需求已清楚但暂无方案的跨模块工作、一个已确认规格的实施、一个微小编辑。核对真实工具输出是否完整，询问是否出现在第一次业务文件修改前，是否等到答案或已有确认后再修改，规格/票据能否被审阅，以及后续切到实施是否保留原选择与版本。对无日志、正文缺失、阶段不同和已经确认的案例分别判定。用已知授权会话记录实际顺序，兼顾复杂任务的提前规划与简单任务的直接完成。

本次新增的是档案基线和两份可定位会话中的行为证据。这些记录支持先改提示并做宿主对照，尚未测得改动后的流程触发率或跨轮保持效果。
