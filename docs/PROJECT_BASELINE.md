- 基准版本：0.2。
- 建立与更新日期：2026-11-04。
- 项目仓库：[LChJo/HarnessL3](https://github.com/LChJo/HarnessL3)；原项目名为 SkillsL3Cli。
- 文档状态：本轮已确认的产品与架构约束；待定项单独列出。
- 实现状态：仓库当前以说明与调研文档为主，CLI、Web、索引和 agent 日志适配能力尚未实现。本文中的验收场景是建设目标，尚未执行产品验收。
- Agent 入口：[AGENTS.md](../AGENTS.md)。
- 背景资料：[开源方案调研](research/open-source-project-visualization-survey-2026-11-04.md)。调研报告保留当时“未选型”的历史状态；当前选型以本基准为准。

## 1. 项目目标

构建面向 agent 的项目上下文管理 CLI：以 LikeC4 文本表达项目全貌，让 agent 用现有文件工具快速理解、维护、更新和增删上下文；通过 Web 服务实时展示项目图、上下文新鲜度及受支持 agent 的读写轨迹。

CLI 能管理多个项目及其分支。每个分支绑定独立 Git worktree，让并行任务的源码、模型、索引和实时状态独立存在并持久化。

性能目标优先考虑查找、读取和写入，接受使用更多磁盘空间保存每个 worktree 的索引、缓存和预计算结果。具体实现和性能数值需后续验证，不宣称已有最优性能。

## 2. 已确认的关键决策

| ID | 决策 | 含义 |
| --- | --- | --- |
| D01 | LikeC4 文本是主模型 | 对象、关系、说明及视图保存在 `.c4` / `.likec4` 文件；agent 直接读写文本 |
| D02 | 不强制增加 agent 操作接口 | Model API、MCP、对象 CRUD 服务不是读写上下文的前置条件；CLI、Web 可有内部接口，但不要求 agent 改用它们编辑模型 |
| D03 | 上下文区分五类信息 | 对象、关系、来源、证据、版本分别表达，保持可关联和可追溯 |
| D04 | 区分三类编辑 | 视图编辑、知识编辑、源码变动有各自的保存和生效机制，源码变动需要反哺上下文 |
| D05 | 每分支独立 worktree | 源码、模型与实时状态并行隔离；CLI/Web 的读写目标必须明确绑定工作区 |
| D06 | 上下文随 Git，本机状态隔离 | 长期上下文可克隆、合并、回溯；索引、缓存、布局预计算和运行记录按 worktree 在本机独立持久化，不进入代码提交 |
| D07 | 查找与读写性能优先 | 接受以空间换性能；具体后端、索引策略及数值预算仍待验证 |
| D08 | 即时标记，阶段结束同步 | 源码变化立即将上下文标记待核验；agent 在阶段结束前同步模型并校验，需要时可提前同步 |
| D09 | 首版包含 agent 读写轨迹 | 从受支持 agent 的现有工具日志采集；未采集的操作标为未知，agent 仍直接读写文件 |

## 3. 文本优先的工作方式

最小闭环：

```text
agent 直接读取、编辑 LikeC4 文本
  → 检测文件变化
  → 解析、校验并更新派生结果
  → Web 刷新图和状态
```

LikeC4 的“模型”指项目对象与关系的结构化文本，不是另一个 AI 模型，也不要求先创建独立对象数据库。内存模型、查询索引、图形数据和渲染缓存均为派生结果，不能成为需要额外手工同步的另一套权威上下文。

CLI 提供项目发现、工作区选择、运行管理、校验、同步状态与 Web 启动等能力；具体命令尚未定稿。agent 的基础入口仍是已有的文件读取、搜索和编辑工具。

同一个对象可以出现在整体、局部、依赖、文档关系等多个视图中，视图共同引用模型。文本可按模块和职责分文件，避免每次操作都读写整份项目模型；具体目录与拆分规范后续确定。

## 4. 上下文的五类信息

| 类别 | 内容 | 基本约束 |
| --- | --- | --- |
| 对象 | 项目、模块、服务、目录、文件、代码符号、文档、需求、测试等 | 选择有助于理解和维护的粒度；首版不预设所有文件和函数都必须入图 |
| 关系 | 包含、依赖、调用、继承、引用、实现、验证等 | 关系有明确类型，不能将不同语义混为一种连接 |
| 来源 | 源码解析、文档引用、人工维护、agent/AI 推断等 | 区分证实事实与推断，不将推断默认为已验证事实 |
| 证据 | 文件、符号、链接、片段或位置，及验证依据 | 摘要与引用可放元数据；详细证据通过稳定标识关联，位置变化后需重新核对 |
| 版本 | 模型版本、对应源码状态、更新时间、验证记录等 | 分支名和 commit 无法独立代表未提交状态，需能识别对应的工作区内容 |

来源和证据摘要使用 LikeC4 元数据、描述与链接表达；详细证据可独立保存并通过标识关联。长期有效的说明与证据引用随 Git 维护，临时运行材料按本机状态管理。具体字段、身份方案和文件格式尚未定稿。

对象与关系应能稳定关联证据和历史，不应仅依赖显示标题。重命名、移动、删除后如何迁移引用，需要在实施前形成契约。

架构文本帮助 agent 定位项目职责、依赖、约束和证据；涉及具体实现时仍应核对相关源码及文档，不能将图的存在视作事实完整或始终最新的证明。

## 5. 三类编辑与源码反馈

| 类别 | 示例 | 保存和生效方式 |
| --- | --- | --- |
| 视图编辑 | 展示范围、布局、样式、分组、注释 | 维护视图定义及人工表达；自动布局预计算属于本机派生数据 |
| 知识编辑 | 增删对象或关系、调整职责、补充来源和证据 | 直接修改权威文本与相关长期说明，再校验和刷新 |
| 源码变动 | 改接口、调用、模块边界或文件位置 | 先形成实际代码变更，再核验相关上下文并更新文本及证据 |

agent 必须能维护视图和知识。Web 是否在首版提供人工拖拽、图形编辑及双向写回，尚未确定；当前已确认的编辑入口是文本。

源码变化后的闭环：

```text
源码变化 → 即时标记待核验 → agent 核查影响
        → 更新模型/证据，或确认无需语义修改
        → 校验并记录所核验的源码状态 → 展示同步结果
```

- 不因每次源文件写入都强制触发一次模型推理。
- 区分源码、模型和派生数据的文件变化；缓存、预计算及事件记录写入不应自行触发源码待核验或无限重建。
- agent 应在任务阶段结束前完成同步及校验；同步失败或未完成时明确保留状态，不能报告为已同步。
- 对不影响架构语义的变更，可记录核验结果，无需为了刷新状态制造虚假的对象或关系变动。
- 同步期间源码再次变化时，不能把对旧状态的核验结果用于宣称新状态已同步。
- 自动检测和依赖定位有助于发现变化，但不默认等于完成语义核验。

“阶段”的精确定义、同步触发契约、影响范围判断和验证记录格式列为实施前待定项。

## 6. 多项目、分支与工作区边界

- 项目是可登记、定位和管理的源码仓库；分支表示代码演进方向；worktree 是实际读写及观测单元，三者应区分。
- 每个受管理分支绑定独立 Git worktree，允许多个分支任务同时存在。
- 模型、索引、缓存、状态和事件明确归属项目与 worktree，不能仅因路径或分支名相似而混用。
- Git worktree 可以共享 Git 对象库；项目上下文运行数据的隔离由本产品实现，不由共享 Git 目录自动提供。
- 切换 Web 视图或 CLI 目标时，不应隐式改变其他任务的工作目录或检出分支。
- 分支隔离不等于同一 worktree 内的并发写入协调；后者的检测和冲突处理需另行确定。

CLI 是否自动创建、清理、归档 worktree，以及删除分支后本机数据的保留策略尚未决定。本轮仅确定隔离单元与持久化方向，没有创建产品工作区或改动现有分支。

## 7. 持久化边界

| 数据 | 存放与版本化 | 地位 |
| --- | --- | --- |
| LikeC4 模型与视图定义 | 业务仓库内，随 Git 分支版本管理 | 权威上下文 |
| 长期说明、证据摘要与引用 | 随 Git 维护 | 可追溯依据 |
| 派生索引、查询缓存、自动布局预计算 | 本机按 worktree 隔离持久化，不进入代码提交 | 可失效、可重建 |
| agent 事件、同步进度、运行记录 | 本机按 worktree 隔离持久化，不进入代码提交 | 运行观测记录 |
| 项目注册、工作区路径等机器信息 | 本机管理；具体目录待定 | 本机管理信息 |

“本机隔离”不预先指定放在 worktree 内的忽略目录，还是 CLI 的外部数据目录；物理路径和后端尚待决定。不能将本次文档工作的 harnesslite/Codux 记录当成未来产品的存储实现。

读取已有模型应能重建可重建的派生数据。运行事件不等于可重建缓存，丢失后不能伪造历史读取记录。备份、保留期限和迁移策略另行确定。

## 8. 性能原则

已确认优先级：查找、读取、写入性能优先；接受空间开销换取性能。

设计与验证方向：

1. 按 worktree 维护独立持久索引和缓存，减少跨分支切换与重建成本。
2. 保留总览和模块定位信息，使 agent 能先理解全貌，再读取相关局部文本。
3. 复用解析结果和预计算数据，避免每次查询都全量扫描、解析和布局。
4. 依据文件及模型版本失效派生结果，尽量只更新受影响内容；实际增量能力需结合 LikeC4 验证。
5. 读写轨迹采集与展示应避免成为普通模型读写的强制阻塞步骤；具体持久化和投递策略待验证。
6. 允许旧图作为明确标记的历史有效结果展示，不将失效缓存冒充当前模型。

这些是性能设计约束与优化方向，不表示已经确定某数据库、索引引擎、进程模型或缓存算法。

后续应分别衡量：冷启动、热查询、文件/对象定位、普通写入、索引更新、图刷新、事件展示、阶段同步和重启恢复。记录 P50/P95、数据规模、硬件、内存及磁盘开销；具体数值预算通过基准后确定。

## 9. Web 展示与状态语义

首版展示范围包含：项目和分支/worktree 选择、项目整体图、局部视图、上下文来源和证据、模型与源码的同步状态，以及受支持 agent 的读写轨迹。

模型有效性与源码新鲜度是两个维度：

| 维度 | 需要表达的状态示例 |
| --- | --- |
| 模型有效性 | 正在解析、校验通过、校验失败 |
| 源码新鲜度 | 已核验到某状态、待核验、同步中、同步失败、未知 |
| 采集覆盖 | 已采集、采集异常、无可用来源/未知 |

模型能成功渲染，并不表示它已反映最新源码。源码已变化而模型尚未更新时，应及时呈现待核验状态。

模型文件暂时无效时，要展示诊断；可以继续显示明确标为旧版本的最近有效图，但不得将其冒充当前有效图。精确状态枚举和转移契约实施前确定。

## 10. Agent 读写轨迹

首版从受支持 agent 的现有工具日志采集文件读取、搜索、修改等实际可获得事件，继续允许 agent 直接使用文件工具。

- 文件变更监听负责观测写入后的变化，不据此推断读取。
- 没有采集证据的操作标为未知；“没有记录”不等于“没有读取”。
- 成功读取文件不等于 agent 已理解它；轨迹反映操作证据。
- 文件级事件可先在文件层显示；只有足够证据定位对象时，才关联或高亮具体模型对象。
- 事件应能定位所属项目、worktree、agent/会话和相关版本；具体事件字段、日志适配协议及去重/补偿策略尚未定稿。
- 采集异常、重启间隙或不支持的工具操作应呈现覆盖状态，不能伪装成完整审计。

首批支持哪些 agent、日志来源是否包含历史补采、如何接入现有工具事件，以及是否由本 CLI 启动 agent，均未决定。不能因为当前协作者是某个 agent，就默认产品已经支持该 agent 的完整日志协议。

| ID | 场景 | 验收要点 |

## 13. 基准文档维护规则

1. 本文件是当前产品与架构约束入口；历史调研和讨论记录用于解释依据，不覆盖较新的已确认决策。
2. 开始任务前读取本文件和 AGENTS.md，定位相关决策、验收场景及待定项。
3. 区分已确认、建议、待定、已实现和已验证。不要把候选方案或计划写成既成能力。
4. 本轮已经授权的常规文档维护可直接执行。改变已确认目标、关键约束或首版范围时，先与用户讨论影响，再按新共识更新；不把例行同步变成重复审批。
5. 目标、数据权威、隔离、同步、轨迹或验收约定发生确认变更时，同一任务更新本文件；若 agent 行为规则变化，同时更新 AGENTS.md。
6. 更新版本、日期和变更记录，说明变了什么、为何改变、关联哪些决策/验收及实现状态。
7. 产品实现与基准有差异时明确记录差距；不为迎合现有实现而悄悄改写目标。
8. 维护内部链接和相关说明入口，不复制多份互相竞争的基准；本文不替代受管理项目自己的 LikeC4 上下文。

## 15. 技术依据

- [LikeC4 Model](https://likec4.dev/dsl/model/)：层级对象、关系、描述、链接及元数据。
- [LikeC4 Views](https://likec4.dev/dsl/views/)：同一模型的多个视角与粒度。
- [LikeC4 CLI](https://likec4.dev/tooling/cli/)：文本文件解析、校验、预览与热更新。
- [LikeC4 AI Tools](https://likec4.dev/tooling/ai-tools/)：可选 skills/MCP 能力，当前不作为 agent 文件编辑的前置条件。
- [Git worktree](https://git-scm.com/docs/git-worktree)：多个工作树、分支检出与共享 Git 数据的边界。
